# 1.5 Orquestación e idempotencia

## Flujo (Prefect, `flows/pipeline.py`)

```
ingesta_batch ─► ingesta_cdc ─► ingesta_streaming ─► vaciar_staging ─► dbt_build ─► verificar_linaje ─► contar ─► exportar_entregables
 (reintentos)     (reintentos)   (Kafka o simulado)    (DROP staging)   (modelos +     (Gold ≠ Bronze)   (evidencia)
                                                                          108 pruebas)
```

Las tareas de ingesta tienen reintentos automáticos. Cada corrida guarda la duración por etapa, el tiempo de consulta y el tamaño por capa en `evidencia/bitacora.log` y `evidencia/metricas-corrida-N.json`.

## Por qué correrlo dos veces no duplica nada

| Capa | Cómo |
|---|---|
| Bronze | Cada archivo se identifica por su hash MD5. Si ya está en `control.ingest_log`, se salta. |
| Kafka | Cada mensaje lleva la llave `<hash>:<línea>`, así el consumidor ignora los repetidos. El offset se confirma solo después de escribir a Bronze. |
| Staging | Se borra al inicio de cada corrida. |
| Silver y Gold | Son tablas que dbt reconstruye desde Bronze: mismo Bronze, mismo resultado. `FECHA_FUTURA` compara contra `_ingested_at` y no contra `now()`, y el ID de Transurbano es el hash del contenido, así que no cambian entre corridas. |
| Evento repetido en otro archivo | Va a cuarentena como `DUPLICADO_REINGESTA`, no se cuenta dos veces. |

## Evidencia: dos corridas con conteos idénticos

Desde cero (sin `lake/` ni `warehouse/`), el 23-sep-2026:

```bash
python flows/pipeline.py --corrida 1
python flows/pipeline.py --corrida 2
python herramientas/comparar.py     # -> 52 tablas comparadas, 0 diferencias -> IDENTICOS
```

Resultado: **IDENTICOS**. Las 52 tablas (Bronze, control, staging, silver y gold) tienen las mismas filas. Archivos: `evidencia/conteos-corrida-1.csv`, `evidencia/conteos-corrida-2.csv` y `evidencia/comparacion-corridas.csv` (columna `identico` en `True` para las 52).

## Rendimiento medido

| Etapa | Corrida 1 (s) | Corrida 2 (s) |
|---|---:|---:|
| Bronze batch | 2.75 | 0.42 |
| Bronze CDC | 0.28 | 0.07 |
| Bronze streaming (simulado, 566,775 eventos línea por línea) | 17.69 | 0.17 |
| Vaciar staging | 0.05 | 0.07 |
| dbt build (modelos + 108 pruebas) | 71.39 | 61.37 |
| Consulta del tablero (demanda por modo × zona × hora) | 56.4 ms | 49.3 ms |

| Capa | Tamaño en disco |
|---|---:|
| Archivos crudos (`datos_red/`) | 136.8 MB |
| Bronze (Parquet) | 31.3 MB |
| Warehouse (staging + silver + gold) | ~486 MB |

El archivo de DuckDB crece en la segunda corrida (a ~849 MB), pero no porque se dupliquen datos: los conteos son iguales. DuckDB no libera el espacio de las tablas que dbt reemplaza. Si hace falta, se compacta con `EXPORT DATABASE` / `IMPORT DATABASE`.

El streaming corrió en modo simulado, que el ingeniero confirmó que es válido para la Fase 1.
